파이썬 8강 · 요약과 통계

두 데이터 합치기

현실의 데이터는 항상 여러 파일에 흩어져 있습니다. 매출은 POS에, 날씨는 기상청에, 주문 내역은 또 다른 곳에. 이걸 붙이는 게 merge 인데, 붙이다 행이 조용히 사라지는 것이 실무 최대의 함정입니다.

이 강의에서 배우는 것
  1. merge의 기본 — 무엇을 기준으로 붙이나
  2. how — 네 가지 붙이기 방식
  3. 행이 사라지는 사고 막기
  4. 행이 늘어나는 사고 (더 위험합니다)
  5. 집계 후 붙이기
  6. concat — 위아래로 쌓기
  7. 실전: 날씨가 매출에 미치는 영향

1. merge의 기본

우리에게는 매출 데이터(cafe_sales.csv)와 날씨 데이터(weather.csv)가 따로 있습니다. 둘 다 date 열을 갖고 있으니 날짜를 기준으로 붙일 수 있습니다.

import pandas as pd sales = pd.read_csv("cafe_sales.csv", parse_dates=["date"]) weather = pd.read_csv("weather.csv", parse_dates=["date"]) print("매출 데이터:", sales.shape, list(sales.columns)) print("날씨 데이터:", weather.shape, list(weather.columns)) print() weather.head(3)

매출은 731행인데 날씨는 708행입니다. 23일치가 없네요. 이 차이가 어떤 결과를 낳는지가 이 강의의 핵심입니다.

합침 = sales.merge(weather[["date", "weather"]], on="date", how="left") print("결과:", 합침.shape) 합침[["date", "visitors", "sales", "weather"]].head(3)
merge 의 3요소
왼쪽.merge( 오른쪽, on="기준열", how="붙이는 방식" )
  • on두 표를 잇는 열쇠가 되는 열. 양쪽에 같은 이름이어야 합니다. 이름이 다르면 left_on, right_on
  • how양쪽에 다 있는 것만 남길지, 한쪽을 다 지킬지 (§2)
  • 기준열 없이인덱스로 붙이려면 left_index=True, right_index=True

2. how — 네 가지 붙이기 방식

for 방식 in ["inner", "left", "right", "outer"]: 결과 = sales.merge(weather[["date", "weather"]], on="date", how=방식) 결측 = 결과["weather"].isna().sum() print(f"how='{방식}':{len(결과):>5}행 weather 결측 {결측:>3}개")
how남는 것우리 경우언제 쓰나
inner 양쪽에 다 있는 날짜만 708행 (23일 사라짐) 양쪽 정보가 모두 필요할 때
left ⭐ 왼쪽 전부 + 있으면 오른쪽 731행 (날씨 결측 23개) 기본 선택. 원본을 지키면서 정보를 덧붙일 때
right 오른쪽 전부 + 있으면 왼쪽 708행 드물게. 보통 순서를 바꿔 left를 씁니다
outer 양쪽 전부 (합집합) 731행 어느 쪽에만 있는지 둘 다 확인하고 싶을 때
기본은 how="left" 입니다 · 분석의 주인공이 되는 표를 왼쪽에 두고, 부가 정보를 붙이는 식으로 생각하세요. inner 는 아무 말 없이 행을 지웁니다. 731일 매출 분석을 하려던 사람이 708일치만 분석하게 되는데, 알아채기가 매우 어렵습니다.

3. 행이 사라지는 사고 막기

merge 전후로 행 수를 확인하는 것을 습관으로 만드세요. 코드 한 줄입니다.

before = len(sales) 합침 = sales.merge(weather[["date", "weather"]], on="date", how="left") after = len(합침) print(f"merge 전 {before}행 → 후 {after}행") if before != after: print("⚠️ 행 수가 바뀌었습니다! 기준열에 중복이 있는지 확인하세요") else: print("✓ 행 수 유지") # 어느 날짜에 날씨가 없는지 확인 누락 = 합침[합침["weather"].isna()] print(f"\n날씨가 없는 날: {len(누락)}일") print(누락["date"].dt.strftime("%Y-%m-%d").head(5).tolist())
검사 = sales.merge(weather[["date", "weather"]], on="date", how="outer", indicator=True) print(검사["_merge"].value_counts().to_string())

indicator=True 를 주면 각 행이 어디서 왔는지 알려주는 _merge 열이 생깁니다.

  • both — 양쪽에 다 있음 (708행)
  • left_only — 왼쪽(매출)에만 있음 (23행 → 날씨 누락)
  • right_only — 오른쪽에만 있음 (0행)

데이터를 처음 붙일 때 이걸 한 번 찍어보면 무엇이 안 맞는지 즉시 보입니다.

4. 행이 늘어나는 사고 (더 위험합니다)

행이 줄어드는 것보다 무서운 게 늘어나는 것입니다. 기준열에 중복이 있으면 merge는 조용히 행을 곱해버립니다.

# 일부러 중복이 있는 작은 표를 만들어본다 왼쪽 = pd.DataFrame({"날짜": ["1일", "2일"], "매출": [100, 200]}) 오른쪽 = pd.DataFrame({"날짜": ["1일", "1일", "2일"], "메모": ["A", "B", "C"]}) print("왼쪽", len(왼쪽), "행 / 오른쪽", len(오른쪽), "행") 결과 = 왼쪽.merge(오른쪽, on="날짜", how="left") print("합친 결과:", len(결과), "행 ← 늘어났습니다!") print(결과.to_string(index=False)) print() print("매출 합계:", 결과["매출"].sum(), " (원래는", 왼쪽["매출"].sum(), ")")
매출이 100원 부풀려졌습니다

"1일"이 오른쪽에 두 번 있어서 왼쪽의 1일 행이 복제됐습니다. 그 결과 매출 100원이 두 번 세어져 합계가 300 → 400이 됐죠.

실무에서 "합계가 왜 안 맞지?" 하는 사고의 절반은 이것입니다. 고객 테이블에 같은 고객이 두 줄 있거나, 상품 마스터에 중복이 있거나… merge 전에 오른쪽 표의 키가 유일한지 반드시 확인하세요.

# validate 를 주면 관계가 깨질 때 '조용히'가 아니라 '오류로' 알려준다 try: 결과 = sales.merge(weather[["date", "weather"]], on="date", how="left", validate="one_to_one") print("✓ 1:1 관계 확인됨 —", len(결과), "행") except Exception as e: print("✗ 관계가 깨짐:", e)
validate 옵션 — 실무에서 꼭 쓰세요
값보장하는 것예
"one_to_one"양쪽 다 키가 유일날짜별 매출 ↔ 날짜별 날씨
"one_to_many"왼쪽만 유일고객 ↔ 주문내역
"many_to_one"오른쪽만 유일주문내역 ↔ 상품마스터

조건이 깨지면 즉시 오류를 냅니다. 잘못된 결과를 들고 회의에 들어가는 것보다 코드가 멈추는 게 백 배 낫습니다.

5. 집계 후 붙이기

메뉴 주문 데이터는 날짜당 여러 행(메뉴마다 한 줄)입니다. 이걸 그냥 붙이면 §4의 폭발이 일어납니다. 먼저 날짜별로 집계한 뒤 붙여야 합니다.

menu = pd.read_csv("menu_orders.csv", parse_dates=["date"]) print("메뉴 데이터:", menu.shape) print(menu.head(3).to_string(index=False)) # 날짜별로 먼저 접는다 (6강의 groupby) 일별 = menu.groupby("date").agg( 총주문=("orders", "sum"), 메뉴종류=("menu", "nunique"), 총액=("amount", "sum"), ).reset_index() print("\n집계 후:", 일별.shape, "← 날짜당 한 행") 합침 = sales.merge(일별, on="date", how="left", validate="one_to_one") print("병합 후:", 합침.shape) print() 합침[["date", "visitors", "총주문", "메뉴종류"]].head(3)
reset_index() 를 잊지 마세요
groupby 결과는 그룹 기준이 인덱스로 들어갑니다. reset_index() 로 다시 일반 열로 꺼내야 on="date" 로 붙일 수 있습니다. 이걸 빼먹으면 KeyError: 'date' 가 납니다.

6. concat — 위아래로 쌓기

merge 가 가로로 붙이는 거라면, concat 은 세로로 쌓는 것입니다. "1월 파일, 2월 파일…을 하나로 합치기" 같은 상황에 씁니다.

상반기 = sales[sales["date"].dt.month <= 6] 하반기 = sales[sales["date"].dt.month > 6] print("상반기", len(상반기), "행 / 하반기", len(하반기), "행") 전체 = pd.concat([상반기, 하반기], ignore_index=True) print("합친 결과:", len(전체), "행") print("원본과 같은가:", len(전체) == len(sales))
ignore_index=True 를 쓰는 이유 안 쓰면 원래 인덱스가 그대로 따라와서 0,1,2… 0,1,2… 처럼 중복됩니다. 나중에 loc 으로 접근할 때 예상 못 한 결과가 나옵니다. 새로 쌓은 표는 인덱스를 새로 매기는 게 안전합니다.

7. 실전: 날씨가 매출에 미치는 영향

합침 = sales.merge(weather[["date", "weather"]], on="date", how="left") 결과 = (합침.groupby("weather") .agg(일수=("visitors", "size"), 평균방문=("visitors", "mean"), 평균매출=("sales", "mean")) .round(1) .sort_values("평균방문")) 결과

깔끔한 순서가 나옵니다. 비(139.9명) < 약한비(171.1) < 구름많음(177.8) < 흐림(179.2) < 맑음(186.3). 날씨가 나쁠수록 손님이 적습니다. 비 오는 날은 맑은 날보다 25%나 적네요.

여기서 한 걸음 더 — 계절을 조심하세요

비는 여름에 집중됩니다. 그런데 여름은 원래 손님이 많은 계절이죠(6강에서 확인). 그렇다면 이 비교는 "비 vs 맑음"이 아니라 부분적으로 "여름 vs 다른 계절"일 수 있습니다.

6강 §7에서 계절을 나눠 확인했을 때는 모든 계절에서 비 오는 날이 적었으므로 방향은 유지됐습니다. 하지만 이런 확인 없이 표 하나를 들고 "비가 매출을 25% 떨어뜨린다"고 말하면 과장입니다. (모듈 08 참고)

# 문제 1. 날씨 데이터가 없는 23일이 특정 기간에 몰려 있는지 확인해보세요. # 힌트: 누락된 날짜의 월별 분포를 세어보기 # 문제 2. 날씨별 '객단가'(매출 ÷ 방문객)를 구해보세요. # 비 오는 날엔 사람이 적게 오는데, 온 사람은 더 쓸까요? # 문제 3. menu_orders.csv 에서 카테고리(커피/라떼기타)별 월 매출을 # pivot_table 로 만들어보세요.

문제 1이 중요합니다. 누락이 한 달에 몰려 있다면 그 달 분석이 통째로 왜곡됩니다. 결과를 보면 12개월에 1~4일씩 고르게 흩어져 있어 상대적으로 안전합니다. 결측은 개수보다 "어디에 몰려 있는가"가 더 중요합니다.

문제 2의 결과가 재미있습니다. 객단가가 비(5,005원) > 약한비(4,969) > 맑음(4,963) > 구름많음(4,945) > 흐림(4,931) — 비 오는 날 온 손님이 가장 많이 씁니다.

방문객 순서(비가 최저)와 정반대죠. 그럴듯한 해석은 이렇습니다 — 비가 오면 "잠깐 테이크아웃"하는 가벼운 손님이 안 오고, 작정하고 앉으러 온 손님만 남기 때문입니다. 일종의 선택 효과입니다.

다만 차이가 74원(1.5%)뿐이라는 점도 함께 보세요. 이 정도 차이가 우연이 아니라고 말할 수 있는지는 13강에서 검정해봅니다.

8강 요약

  • merge(오른쪽, on="키", how="방식") — 가로로 붙이기.
  • how="left" 가 기본. inner 는 말없이 행을 지운다(731→708).
  • merge 전후로 행 수를 반드시 확인. 줄어들면 키 불일치, 늘어나면 중복 키.
  • 행이 늘어나는 게 더 위험하다 — 합계가 조용히 부풀려진다.
  • validate="one_to_one" 으로 관계를 코드에 못박아 두자.
  • indicator=True 로 어느 쪽에만 있는지 확인.
  • 1:N 데이터는 먼저 집계한 뒤 붙인다(reset_index() 잊지 말 것).
  • concat 은 세로로 쌓기. ignore_index=True 를 쓸 것.
